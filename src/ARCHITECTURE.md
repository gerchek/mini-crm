# Архитектурные и технические решения

## Выбор библиотек

### spatie/laravel-permission
Выбрана для управления ролями (manager, admin), так как это де-факто стандарт в экосистеме Laravel. Пакет предоставляет готовые миграции, middleware и trait `HasRoles`, что позволяет не писать собственную систему авторизации. Роли проверяются через middleware `EnsureUserIsManager`, который допускает пользователей с ролью `manager` или `admin`.

### spatie/laravel-medialibrary
Требование ТЗ — привязка файлов к заявкам. Пакет берёт на себя хранение, именование и отдачу файлов, поддерживает коллекции (используется коллекция `attachments`). Альтернатива — ручное хранение через `Storage`, но это потребовало бы написания собственной логики управления файлами без явных преимуществ.

### darkaonline/l5-swagger
Используется для автогенерации Swagger/OpenAPI документации из PHP-атрибутов. Документация доступна по адресу `/api/documentation` и всегда синхронизирована с кодом.

## Архитектурные решения

### Service Layer (TicketService)
Бизнес-логика вынесена в `App\Services\TicketService`, а не размещена в контроллерах. Это обеспечивает:
- **Single Responsibility** — контроллеры отвечают только за HTTP, сервис — за бизнес-логику.
- **Переиспользование** — один сервис используется и в API-контроллере, и в админ-контроллере.
- **Тестируемость** — сервис можно тестировать изолированно.

Сервис содержит методы:
- `createTicket()` — создание клиента (firstOrCreate) и заявки в транзакции.
- `canSubmitTicket()` — проверка лимита (1 заявка/сутки на email или телефон).
- `searchTickets()` — поиск и фильтрация заявок для админки.
- `updateStatus()` — смена статуса с автоматическим проставлением `responded_at`.
- `getStatistics()` — подсчёт заявок за день/неделю/месяц через Carbon.

### API Resources
Все API-ответы оформлены через Laravel API Resources (`TicketResource`, `CustomerResource`, `MediaResource`, `TicketStatisticsResource`). Это даёт единообразный формат ответов, контроль над структурой JSON и возможность изменить формат без правки контроллеров.

### Form Requests
Валидация вынесена в `StoreTicketRequest`. Телефон валидируется регулярным выражением E.164 (`^\+[1-9]\d{1,14}$`). Это разделяет ответственность — контроллер не содержит правила валидации.

### Rate Limiting
Реализовано на уровне сервиса (`canSubmitTicket`), а не через стандартный middleware `throttle`. Причина: ограничение привязано к бизнес-данным (email/телефон клиента), а не к IP-адресу или пользователю. Проверяется наличие заявки за текущие сутки через `whereDate('created_at', Carbon::today())`.

### Виджет и iframe
Виджет — отдельная Blade-страница на маршруте `/widget`. Middleware `AllowIframeEmbedding` удаляет заголовок `X-Frame-Options` и устанавливает `Content-Security-Policy: frame-ancestors *`, чтобы страницу можно было встроить через `<iframe>` на любой домен. Форма отправляется через AJAX (fetch API) на `/api/tickets` без перезагрузки страницы.

### Админ-панель
Реализована на Blade без JavaScript-фреймворков — для простого CRUD это оптимальный выбор (KISS). Фильтрация работает через GET-параметры с `when()` в Eloquent-запросах. Пагинация сохраняет параметры фильтров через `withQueryString()`.

### Статусы заявок
Статусы (`new`, `in_progress`, `processed`) хранятся как константы в модели `Ticket` (`STATUSES`, `STATUS_NEW`, `STATUS_IN_PROGRESS`, `STATUS_RESOLVED`). При смене статуса на любой кроме `new` автоматически проставляется `responded_at` — дата ответа менеджера.

## Структура Docker

- **app** — PHP 8.4-fpm с расширениями для Laravel (pdo_mysql, gd, zip и др.).
- **db** — MySQL 8.0 с healthcheck для ожидания готовности перед стартом app.
- **nginx** — Reverse proxy, проксирует PHP-запросы в app через FastCGI на порт 9000.

Volumes: исходный код монтируется в контейнеры через bind mount (`./src:/var/www`), данные MySQL сохраняются в named volume `dbdata`.
